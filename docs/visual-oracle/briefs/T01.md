## Scope

Decide how the harness captures a rendered SWT widget as a PNG. Compare three strategies experimentally on Linux/GTK and write an ADR recommending one.

Strategies to compare:
1. `Control.print(GC)` into an `Image`, per widget.
2. `new GC(control)` plus `GC.copyArea(Image, x, y)`, per widget.
3. Full-shell capture under Xvfb via an X11 grab (`import -window root`, ImageMagick, already installed), cropped to widget bounds.

## Evaluation criteria, in priority order

1. **GL content fidelity. This is the decisive criterion.** The Skia canvas backend renders into a GLX child window (`gdk_window_new` plus a GLX context), not into the cairo surface of the widget. A capture strategy that reads back the cairo surface may therefore produce an empty or stale image for exactly the widgets this harness exists to compare. Test this explicitly: build a `Canvas` with style `SWT.SKIA` (see step 3 of the build recipe below), draw known content into it, and check whether each strategy captures the drawn pixels. If a strategy cannot see GL content, say so plainly with the evidence; that alone disqualifies it.
2. **Determinism.** Capture the same specimen five times in one process and five times across five processes. Report whether the bytes are identical, and if not, where they differ.
3. **Crop precision.** Does the strategy give you exactly the widget bounds, and are coordinates correct at zoom 100 and zoom 200 (`-Dswt.autoScale=200`)?
4. **Speed.** Milliseconds per capture, measured over at least 50 captures.
5. **Win32 portability.** Assessed by reading the SWT sources in this repo only. There is no Windows machine available. State clearly which parts of your conclusion are unverified.

## How to run anything graphical

Always, without exception:

```bash
env -u WAYLAND_DISPLAY -u XDG_SESSION_TYPE GDK_BACKEND=x11 LIBGL_ALWAYS_SOFTWARE=1 \
  xvfb-run -a -s "-screen 0 1600x1200x24" <your command>
```

Unsetting the Wayland variables is mandatory. With them set, `xvfb-run` silently renders on the real compositor, the run is not headless, and on any failure GNOME pops a screen-share dialog that blocks for 15 seconds. `LIBGL_ALWAYS_SOFTWARE=1` gives you llvmpipe, which is required because Xvfb has no GPU.
