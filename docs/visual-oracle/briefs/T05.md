# T05: Environment control

You are working on the SWT Visual Oracle, a harness that renders each SWT widget through a native backend and a Skija backend and diffs the images, so renderer work can be verified by machine instead of by a person looking at screenshots.

Read first, they are the specification and this brief does not restate them:

- `docs/visual-oracle/SPI.md`, the frozen SPI, authoritative, especially "Process model" and `RenderEnv`, `Theme`, `Direction`
- `docs/visual-oracle/PLAN.md`, especially decision D6 and the T05 row of the task table
- `docs/visual-oracle/TRACKING.md`, sections "Work protocol" and "Quality bar"

Six tasks are merged. `tools/oracle/build.sh <backend>` prints a classpath, `tools/oracle/build-harness.sh` compiles the harness, `tools/oracle/oracle selftest` passes 15 of 15 and must stay green.

## Why this task exists

SWT reads zoom, theme and text direction once at `Display` creation, and each backend links its own natives and class output. One process therefore serves exactly one backend and exactly one `RenderEnv`, which is decision D6 in `PLAN.md` and the reason `Capture` throws `UnsupportedEnvironmentException` when asked for anything else.

A full comparison consequently spans many processes. Someone has to spawn them, feed each one the right environment, collect what they produce and fail intelligibly when one of them dies. That is this task.

## Scope

1. **Environment definition.** Turn a `RenderEnv` into the concrete process configuration that realises it: the environment variables and system properties for zoom, theme and text direction. `impl/SwtRenderEnvs` already reads the current process's environment; you own producing the launch configuration for a requested one.

   On Linux this means the GTK theme (`GTK_THEME`), the SWT zoom property, and the mirrored/right-to-left setting. Verify each one actually takes effect rather than assuming: an environment variable that is silently ignored produces a run that claims to test 200 percent zoom while rendering at 100, which is worse than not testing it at all, because the report will say it passed.

2. **Process launcher.** Spawn a child JVM for one (backend, environment) pair, run a requested set of specimens in it, and return their results. The child already exists in spirit: `tools/CaptureProbe` captures one specimen in a child process and prints a line. Generalise that into something the harness can drive for many specimens.

3. **Result collection.** Each child produces result JSON per the frozen schema. Merge the children's output into one run result. The JSON is the comparison substrate, per D6, so do not invent a second interchange format.

4. **Failure isolation.** A child that crashes, hangs or exits non-zero must not take down the run: record it as a failure with its stderr and continue. A hung child must time out. Given the process count, an unbounded hang would otherwise strand the whole matrix.

5. **Parallelism, bounded.** Several children can run at once. Measure how many this machine sustains before results get slower or flakier, state the number, and make it configurable rather than hardcoded. Each child needs its own Xvfb display; two children sharing one display will interfere.

## Explicitly not in scope

Comparing across backends and producing verdicts (T20), the HTML report (T19), the diff engine (T06, being rewritten in parallel by another agent), the specimen catalog (T14 and T15, being extended in parallel).

Do not modify `build.sh`, `verify-backend.sh`, anything under `spi/`, `impl/CaptureRuntime.java`, `impl/ExactDiffer.java`, or anything under `catalog/`. Other agents are working in those files right now.

## Check your own work

```bash
tools/oracle/build-harness.sh && tools/oracle/oracle selftest
```

All 15 checks must stay green, and you add checks for what you build. At minimum:

- a child process launched for zoom 200 genuinely renders at zoom 200, proven by the captured image size rather than by the property being set
- a child launched for a right-to-left environment genuinely mirrors, proven by pixels differing from the left-to-right capture of the same specimen
- a child that exits non-zero is recorded as a failure with its stderr, and the run continues
- a child that hangs is timed out and recorded, and the run continues
- results merged from two children validate against the frozen result schema

The first two matter most. An environment control that silently does nothing is the most dangerous possible outcome of this task, because every later result would carry a label that is a lie.

## Rules earlier tasks in this project learned the hard way

**Scratch goes in `/tmp/opencode/oracle-t05/` and nowhere else outside this worktree.** Other external paths are auto-rejected non-interactively and your run stops with no useful error.

**Never read PNG or other image files into your context.** Use ImageMagick from the shell (`compare -metric AE a.png b.png null:`, `identify`) and quote only the numbers. Reading images is the likeliest cause of the provider stream drops that cost an earlier task six sessions.

**Commit early, amend as you go.** The endpoint drops streams unpredictably; a driver resumes you automatically, but only committed work survives cleanly.

**Never weaken a check to make it pass.** Fix the cause, and never mark verified what you did not run.

**Do not push and do not open a pull request.**

## Running anything graphical

Always, without exception:

```bash
env -u WAYLAND_DISPLAY -u XDG_SESSION_TYPE GDK_BACKEND=x11 LIBGL_ALWAYS_SOFTWARE=1 \
  xvfb-run -a -s "-screen 0 1600x1200x24" <command>
```

With the Wayland variables set, `xvfb-run` silently renders on the real compositor and the run is not headless. `xvfb-run -a` picks a free display number, which is what lets several children run at once.
