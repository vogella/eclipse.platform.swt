## Scope

The range widgets: `Scale`, `Slider`, `ProgressBar` and `ScrollBar`.

Cover, at minimum:

`Scale`: horizontal and vertical, at minimum, midpoint and maximum, with a non-default page increment, and disabled.
`Slider`: horizontal and vertical, thumb at start, middle and end, with a thumb size that differs from the default, and disabled.
`ProgressBar`: horizontal and vertical, at 0, 50 and 100 percent, `SWT.SMOOTH`, and both the `PAUSED` and `ERROR` states.
`ScrollBar`: taken from a scrollable host, horizontal and vertical, at different positions.

Aim for coverage that would catch a real renderer defect, not for a specimen count. A `Slider` whose thumb is drawn one pixel off at the maximum position is exactly the defect this family exists to catch, so include the extremes rather than only the midpoint.

Contribute them as `SpecimenModule` implementations in `org.eclipse.swt.visualoracle.catalog`, one module per family, discovered automatically. **Never add a central registration list**: other agents are adding other families in parallel, and a shared list would make every one of them conflict. Add files, do not edit shared ones.

Ids are lowercase dot-separated and stable forever: `scale.horizontal.max`, `progressbar.smooth.50`, `slider.vertical.thumb-large`.

## The hard part: indeterminate progress is an animation

`SWT.INDETERMINATE` on `ProgressBar` animates forever and can never be captured deterministically. Do not include it, and say so in your handoff rather than leaving a reader to wonder whether it was forgotten.

Determinate progress bars may also animate *to* their value on some themes: setting 50 percent can slide from 0 to 50 rather than appearing at 50. The capture runtime returns a capture only once a rendering has persisted byte-identical across a live observation window, so such a specimen either settles at its final value or fails loudly. If a specimen cannot settle, measure it and drop it with the evidence.

`ScrollBar` cannot be created standalone; take it from a scrollable host and capture the host, or capture the scrollbar's own bounds if that proves stable. Say which you did and why.

Tag anything focus-dependent with `Tag.FOCUS_SENSITIVE`.

## Rules earlier tasks in this project learned the hard way

**Scratch goes in `/tmp/opencode/oracle-t17/` and nowhere else outside this worktree.** Other external paths are auto-rejected non-interactively and your run stops with no useful error.

**Never read PNG or other image files into your context.** Use ImageMagick from the shell (`compare -metric AE a.png b.png null:`, `identify`) and quote only the numbers. Reading images is the likeliest cause of the provider stream drops that cost an earlier task six sessions.

**Commit early, amend as you go.** The endpoint drops streams unpredictably; a driver resumes you automatically, but only committed work survives cleanly. Commit as soon as the first family builds.

**Never weaken a check to make it pass.** Fix the specimen or drop it with evidence.

**Do not push and do not open a pull request.**

## Running anything graphical

Always, without exception:

```bash
env -u WAYLAND_DISPLAY -u XDG_SESSION_TYPE GDK_BACKEND=x11 LIBGL_ALWAYS_SOFTWARE=1 \
  xvfb-run -a -s "-screen 0 1600x1200x24" <command>
```

With the Wayland variables set, `xvfb-run` silently renders on the real compositor and the run is not headless.
